# 半年制硕士论文协作与研究节奏规则

## 1. 文件用途

本文件是本项目的长期协作规则，用于约束 GPT、Codex 和学生在半年论文周期内如何制定计划、执行研究、交换反馈和推进 Git 版本。

它不是 PEM/RWTH 官方规定，也不是 Thomas 的逐字要求。它是学生确认采用的**项目工作协议**。如与 Thomas 的最新明确反馈冲突，以 Thomas 的反馈为优先；如涉及正式论文要求，以最新 PEM/RWTH/ZPA 规定为准。

## 2. 总体原则：慢一点、稳一点

本项目是 Master Thesis，不按博士课题或工业交付项目设置标准。

论文需要做到：

- 问题边界清楚；
- 文献和证据可信；
- 方法能够回答研究问题；
- 推理过程透明；
- 结果在所用假设下可复现；
- 局限性说明清楚。

论文不强求：

- 提出复杂的新算法；
- 建立全球通用框架；
- 同时研究大量变量和案例；
- 获得大规模真实工厂数据；
- 建立可以直接部署的工业系统；
- 每周产生重大结论；
- 为了显得学术而提前加入 optimization、robustness、multi-objective、AI 或 ROI。

一个范围有限、逻辑完整、证据扎实、经过适当验证的案例研究，符合本项目的目标。

## 3. 每周只推进一个核心问题

每周计划必须包含：

1. **本周核心问题**：这一周真正要理解的一个问题；
2. **为什么现在研究它**：与前一周成果、导师反馈和论文方向的关系；
3. **Day 1–5建议**：学习顺序，不是硬性每日KPI；
4. **最低完成目标**：完成到这里，本周即为合格；
5. **有余力再做**：不影响主线的可选扩展；
6. **明确不做事项**：防止范围扩大；
7. **学生应学会什么**：能够用自己的话解释的内容；
8. **周末检查点**：是否继续、补学或调整，而不是自动升级阶段。

Day 1–5 可以跨周。没有读懂 Day 2 时，不为了凑满五天强行进入 Day 3。某个基础步骤多花一到两周是正常的。

## 4. 三方角色

### 4.1 GPT：周方向与外部审查

GPT主要负责：

- 提出每周唯一核心问题；
- 给出宽松、可执行的 Day 1–5方向；
- 解释本周为什么值得研究；
- 阅读 GitHub 已推送的最新成果；
- 检查是否浮于表面、范围过大或推理跳跃；
- 指出事实、推断、假设和证据缺口；
- 根据 Thomas 最新反馈提出下一周计划。

GPT的计划是提案，不自动成为研究决定。GPT不应在每次审查时增加新的复杂变量或把题目升级为复杂优化问题。

### 4.2 Codex：执行、证据审查与项目维护

Codex主要负责：

- 阅读本地完整仓库、当前周文件和导师反馈；
- 审查GPT计划的工作量、证据基础与阶段适配性；
- 精读原始文献，核查页码、章节、DOI和证据边界；
- 区分文献事实、企业说法、工程推断和未知项；
- 制作学习材料、证据表、流程图、事件表和必要的代码；
- 维护 known–inferred–unknown 和研究决策记录；
- 保持本地文件、Git版本和远端GitHub内容一致；
- 在推送前检查引用、逻辑、文件结构和未确认结论。

Codex不是机械执行GPT的所有建议。若建议过宽、过早、证据不足或与导师反馈冲突，Codex应明确修正并说明原因。

### 4.3 学生：学习者与最终决策者

学生主要负责：

- 真正理解每周核心问题；
- 用自己的话复述本周所学；
- 指出未理解、节奏过快或与个人认知不符的内容；
- 决定是否接受当前工作方向；
- 参加组会并尽量原样带回 Thomas 的反馈；
- 确认周成果是否可以提交和推送。

学生不是以文件数量考核AI的项目管理员。每周最重要的成功标准是：

> 学生是否比上周更清楚地理解了研究对象。

最终答辩者是学生，因此任何关键概念和结论都必须能由学生解释。

## 5. Thomas反馈闭环

Thomas 的明确反馈拥有最高的研究方向调整优先级。

每次组会后采用：

```text
学生带回原始反馈或尽可能完整的记录
→ Codex整理，但不擅自扩展导师含义
→ GPT结合GitHub周成果进行外部审查
→ 明确区分四类信息：
   1. Thomas明确要求
   2. GPT/Codex对反馈的解释
   3. 当前工作假设
   4. 尚未确定的问题
→ 制定或修正下一周计划
```

如Thomas的反馈与当前工作假设冲突，应修正假设，不应为了维护原计划而选择性解释导师意见。

## 6. GitHub周循环

推荐循环：

```text
GPT读取GitHub并提出周计划
→ Codex核查计划
→ 学生确认本周核心问题
→ Codex在本地执行并维护证据
→ 学生学习并反馈理解情况
→ Codex完成周末检查
→ 学生确认可以push
→ Codex commit并push至GitHub
→ GPT读取远端最新版本，反馈并提出下一周计划
```

注意：

- GPT通常只能看到已经推送的远端版本；
- Codex能看到本地未提交变化；
- 不把未确认的工作假设包装成正式结论后推送；
- Codex在学生确认前不自动提交或推送周成果；
- Git提交应表达本周实际完成内容，不夸大研究成熟度。

## 7. 每周成果的轻量结构

不要求每天生成一个大文件。只在内容可复用时写入仓库。

一个周文件夹通常可以包含：

```text
README.md                  本周核心问题、范围与节奏
day*_learning_guide.*      必要的每日学习材料
literature_evidence.md     核心文献、页码与证据链
known_inferred_unknown.md  已知—推断—未知
week_summary.md            本周真正得到的结论
next_questions.md          未解决问题与下周入口
```

可以合并文件，不以文件数量作为进度指标。

## 8. 阶段推进条件

不得采用以下自动推进逻辑：

```text
选案例 → 立刻找gap → 立刻写代码 → 立刻优化 → 立刻算ROI
```

推荐逻辑：

```text
理解工艺
→ 理解对象、任务和接口
→ 理解机器人/AGV系统
→ 梳理已有研究并寻找反例
→ 提出候选gap
→ 判断数据、方法和验证是否可行
→ 再决定是否建模、仿真或评价
```

只有当前一步的最低理解目标达到后，才讨论下一阶段。即使工具和代码容易实现，也不能用实现速度替代研究理解。

## 9. 当前Week 03适用解释

当前学习案例是 cell finishing 中 formation–aging–testing 之间的托盘运输。

Week 03最低完成目标是学生能够解释：

> 一盘电芯为什么移动、怎样交接、在哪里等待、延迟可能造成什么影响，以及哪些内容有文献支持、哪些只是推断、哪些仍不知道。

本周不要求：

- 确定最终research gap；
- 编写SimPy模型；
- 优化AGV数量或调度；
- 讨论稳健性、多目标或ROI；
- 为赶进度完成全部Day 1–5。

先把Day 2的cell-finishing工艺和托盘物流含义理解扎实，再进入Day 3。
