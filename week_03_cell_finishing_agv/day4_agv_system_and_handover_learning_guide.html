Week 03 · Day 4 · AGV系统基础带教

托盘请求产生以后，
AGV系统到底决定什么？

今天不学习某个调度算法。我们只把生产系统、车队控制、移动机器人与设备交接的责任边界画清楚，避免把所有物流问题都叫作“AGV调度”。

今日目标责任层级决策分类设备交接订单闭环VDA 5050案例推演自测

0. 今天学到什么就算完成？

Production

知道谁定义物料需求和工艺释放，而不是让AGV决定电芯工艺。

Fleet control

理解任务分配、路线、交通和充电属于什么层级。

Mobile robot

理解车辆执行移动、取放、定位并回报状态。

Handover

理解到站不等于完成，物理接口可能有固定设备参与。

最低目标：看到一个问题时，能判断它属于工艺层、任务/车队控制层、车辆执行层还是设备交接层。今天不比较算法优劣。

Day 3已经解释了请求从哪里来。Day 4只研究中间两格：车队控制如何组织任务，以及车辆和接口怎样执行。

不要把这三句话混在一起：“需要把哪盘电芯送走”来自生产物流需求；“派哪台车”是任务分配；“车辆怎样绕开障碍并准确停车”属于车辆导航/运动与接口执行。

2. 四层责任：谁决定什么？

下面是用于学习的通用架构，不是目标工厂已经确认的IT结构。

层级典型问题在本案例中的例子不能自动假定
Process / production control什么产品完成？下一目的地和优先级是什么？何时允许释放？Formation完成的tray是否可以去RT-aging storage。具体由MES、PLC、WMS还是人工规则发请求仍未知。
Fleet control / MCS任务分给哪台车？走哪条可行路线？怎样避免冲突？何时充电或停车？从可用车辆中选择一台服务formation出口。VDA 5050定义通信接口，不替项目提供具体调度算法。
Mobile robot怎样定位、沿路线/自主路径移动、执行pick/drop并报告状态？到formation handover point，取得tray并驶向aging入口。不能假设任何AGV都能直接抓取目标tray或进入工艺设备。
Handover / peripheral equipment怎样对中、转交、锁定、识别并确认载荷？滚筒port、升降机或固定transfer unit把tray交给车辆。真实接口可能是直接取放，也可能经过固定设备。
工业规范证据：VDA 5050 v3.0.0, Section 5.1，PDF pp. 10–11将参与者概括为operator提供基础信息、fleet control组织管理运行、mobile robot执行订单；具体生产IT系统不属于该规范定义的接口范围。

3. 七类常被混称为“AGV调度”的问题

概念它回答的问题例子当前定位
Fleet sizing系统配置多少台车？两台是否足够服务formation和EoL任务？未来候选变量
Dispatching / task allocation当前任务分给哪台可用车，或哪项任务先服务？车辆A离formation更近，车辆B电量更高，派谁？未来候选变量
Routing车辆从起点到终点使用哪条路径？走短路还是绕开拥堵路段？本周只识别
Traffic control多车共享路段时怎样避免冲突、拥堵和deadlock？窄通道一次允许哪台车通过？本周只识别
Idle positioning / parking没有任务时车辆停在哪里？停在中央还是formation附近？以后再判断
Charging / energy management何时、去哪充电，是否中断可服务能力？空闲时机会充电还是低电量强制充电？背景约束
Handover control车辆、port与设备怎样安全完成pick/drop？目标port被占用时是否等待或重试？当前重要接口问题
两个最容易混淆的概念：dispatching决定“派谁/先做谁”，routing决定“从哪里走”。给同一台车分配同一任务，仍可能存在多条路线选择。
学术依据：Vis (2006), European Journal of Operational Research 170(3), pp. 677–709系统回顾AGV系统设计与控制问题；De Ryck et al. (2020), Journal of Manufacturing Systems 54, pp. 152–173进一步讨论中央式与分布式AGV控制技术。本笔记只借用问题分类，不引入其算法。

4. Route、navigation和motion不是同一层

Route / path in network

在节点—边网络或区域之间决定经过哪些路段，是车队协调关心的系统级问题。

Navigation / localization

车辆知道自己在哪里，并依据地图、轨迹或目标位置移动。

Motion / local execution

车辆控制速度、转向、避障和精确到位，属于更接近底盘与安全执行的层级。

VDA 5050 v3.0.0同时覆盖line-guided和freely navigating mobile robot：前者遵循预定义轨迹；后者可以自行规划轨迹，但fleet control仍可通过订单、区域和交通协调施加约束。

直接证据：VDA 5050 v3.0.0, Sections 3.6–3.7，PDF p. 8；Sections 5.3–5.4，PDF pp. 11–12。规范把订单分配、特定路线/交通/能量协调列为fleet control功能，把定位、路线执行、动作执行和持续状态报告列为mobile robot功能。
范围控制：我们的论文现在不研究SLAM、局部路径规划、避障控制或轮式底盘动力学。它们可能影响可行性，但不是Week 03核心问题。

5. AGV不一定直接和Formation设备交接

设备之间存在运输需求，不代表车辆必须把货叉或滚筒伸进工艺设备。至少有三种候选架构：

A. Direct handover

车辆的load-handling device直接与设备port交接。需要精确定位、互锁和载荷确认。

B. Fixed transfer point

工艺设备先把tray送到conveyor/roller port，AGV只在标准handover point取放。

C. Lift / gantry / robot

固定设备负责高度变化、精密装卸或多层rack存取，AGV负责区域间水平运输。

Process equipmentFormation/EoL
↔
Fixed transferConveyor/Lift/Gantry
↔
Handover point标准取放口
↔
Mobile robot区域运输

交接至少要确认什么？

  • 来源位置确实有正确载荷，目标位置确实可接收；
  • 车辆和port到位，相关动作允许执行；
  • pick/drop物理动作成功，载荷没有卡住或遗留；
  • 产品/托盘身份和任务状态得到一致更新。
接口示例证据：VDA 5050 v3.0.0, Section 6.2.3及Table 5，PDF pp. 27–38定义了pick、drop、finePositioning和waitForTrigger等动作及成功/失败状态。这证明通用移动机器人接口会表达这些动作，不证明cell-finishing工厂采用哪种物理port。

6. 从生产请求到车辆状态的闭环

1 Production need托盘ready、目标确定
→
2 Fleet control分配车辆、形成order
→
3 Mobile robot接收并执行
→
4 Pick / drive / drop动作与移动
→
5 State report位置、载荷、动作和错误
↺
6 Fleet update继续、重试或结束

在VDA 5050的通信方向中，fleet control向车辆发布order；车辆持续向fleet control发布state。车辆完成最后节点及相关动作后进入idle并可接收新订单。

直接证据：VDA 5050 v3.0.0, Sections 4.3、5.1、6.1.2.1，PDF pp. 9–11、18。规范的order/state闭环可帮助我们理解责任边界，但目标工厂是否采用VDA 5050仍是unknown。
连接Day 3：车辆报告drop完成，只说明载荷已离开车辆。生产系统是否同步确认正确tray进入正确EoL任务，还需要项目特定的外围系统和状态一致性设计。

7. VDA 5050能告诉我们什么，不能告诉我们什么？

它能支持的理解它没有替我们解决的内容
中央fleet control与不同移动机器人可以使用vendor-neutral接口交换order和state。Formation、aging和EoL何时产生运输请求。
可以表达节点/边、动作、载荷、错误和车辆状态等信息。哪种dispatching或routing算法最好。
规范列出了fleet control和mobile robot的最低功能。外围设备、MES/PLC/WMS接口的完整架构。
v3.0.0兼顾line-guided与freely navigating mobile robots。安全要求、网络安全措施和项目责任分配。
它可作为工业接口背景和术语来源。不能证明电池工厂已经使用，也不能证明AGV适合我们的案例。
官方边界：VDA 5050 v3.0.0, Section 2，PDF pp. 6–7明确排除安全要求、交通管理算法、外围/外部IT接口、实施流程、责任分配和网络安全措施。因此不能把“符合VDA 5050”理解为整个AGV系统设计已经解决。
来源类型：VDA 5050是VDA/VDMA工业推荐规范，不是同行评审论文；可用于接口事实与工业背景，不替代AGV学术综述或cell-finishing工艺文献。

8. 用一个小场景区分四类问题

假设formation出口有托盘F，aging出口有托盘A；两台车R1和R2可用。

问题属于哪一层为什么
托盘F和A谁更紧急？生产优先级 + dispatching输入优先级应与工艺、等待后果和生产规则有关，不能由车辆随意决定。
把F分给R1还是R2？Task allocation / dispatching在任务与车辆之间建立匹配。
R1经过通道X还是Y？Routing决定从当前点到取货/交付点的路径。
R1和R2同时想进入窄通道怎么办？Traffic control协调共享空间并避免冲突或deadlock。
R1到formation口但托盘没有被推出。Handover/peripheral interface车辆到站了，但取货条件或设备动作没有完成。
Formation协议是否已经满足质量要求？Process/quality control这是电芯工艺判断，不属于AGV控制。
Day 4最重要的能力：以后看到“AGV造成延迟”，先定位延迟究竟来自任务未创建、派车晚、路线拥堵、车辆故障，还是handover失败。不同原因不能用同一种算法解决。

9. 当前为什么只保留fleet size和dispatching为候选？

与Day 3直接相连

车辆数量和任务分配会直接影响托盘等待服务的时间，进而可能影响formation blocking和EoL starvation。

但仍未成为研究问题

只有确认运输任务、接口、需求变化和验证数据后，才能判断它们是否值得成为论文变量。

Routing、parking、charging、robustness等不是不重要，而是当前没有必要同时展开。先保留完整系统意识，再收缩变量。

当前合格表述：Fleet size and dispatching remain candidate AGV-system decisions because they may affect tray waiting and equipment starvation/blocking. Their research relevance has not yet been established for the selected cell-finishing scenario.

10. 第一版“已知—推断—未知”

状态Day 4内容
FACTAGV研究通常区分系统设计、任务分配、routing、traffic、parking和energy等问题；VDA 5050 v3.0.0定义fleet control—mobile robot的order/state接口及最低功能边界。
INFERENCE如果cell-finishing任务由移动机器人承担，fleet size和dispatching可能通过任务waiting影响设备blocking/starvation；标准handover point可能把区域运输与精密设备装卸解耦。
UNKNOWN目标场景是否使用AGV/VDA 5050；请求由谁生成；直接交接还是固定transfer；车辆能力、路线、交通、充电、异常恢复和系统责任边界。

11. 自测：先判断，再展开

Q1. MES要求把tray送到EoL，这已经完成dispatching了吗？

没有。这只是形成运输需求/任务。Dispatching还要决定由哪台车服务，或者多项任务中先服务哪一项。

Q2. Fleet control把任务分给R1以后，routing也完成了吗？

不一定。任务分配回答“派谁”，routing回答“走哪条路径”。两个决定可能在同一系统中计算，但概念不同。

Q3. AGV到站后pick失败，这是routing问题吗？

通常不是。车辆已经到站，问题更可能位于handover、载荷状态、精确定位、互锁或外围设备接口。

Q4. VDA 5050是否规定了最佳交通控制算法？

没有。v3.0.0明确把routing、prioritization、congestion和deadlock resolution等交通管理逻辑排除在规范范围之外。

Q5. 为什么固定conveyor/lift仍可能出现在AGV案例里？

AGV可负责区域运输，固定设备负责设备内部或多层rack的精密装卸。两者通过handover point组合，而不是互相排斥。

13. 第一轮复述复盘：两个核心混淆

本轮已经理解生产控制、dispatching、routing和handover的大方向，但“车队设计—车队控制—车辆执行”仍混在一起。下面用一项Formation取货任务重新固定。

混淆一：Fleet control不是“决定有几台车”

Fleet sizing规划阶段决定配置几台车
≠
Fleet control运行阶段管理现有车辆
→
Mobile robot执行被分配的订单
概念一句话Formation取货例子
Fleet sizing决定系统需要配置多少台车及相应运力，不是车身长宽尺寸。规划阶段判断两台、三台还是更多车辆才能满足候选需求。
Fleet control系统运行时组织和管理已有车队。当前有R1、R2两台车，决定把Formation任务派给R1，并协调路线、交通和充电。
Mobile robot接收订单后在物理世界执行。R1定位自身、驶向取货点、执行pick、载货行驶、drop并持续报告状态。
记忆句：sizing = 需要几台；dispatching = 这次派谁；robot execution = 被派的车实际去做。

混淆二：交通控制不是单纯“制定交通规则”

Fleet sizing

规划多少台车。

Dispatching

任务与车辆怎样匹配、任务先后怎样选择。

Routing

某台车从当前点到目标点走哪条路径。

Traffic control

多车共享路口、窄道等资源时，实时协调通行，避免冲突、拥堵和deadlock。

为什么到站仍可能取货失败？不要只堆系统缩写

PLC、WMS或其他系统可能参与实现，但在不知道真实架构时，列出缩写并不能解释失败原因。应先描述可观察的接口条件：

  • 车辆是否准确停到可交接位置；
  • formation port是否真的有正确托盘，并已允许释放；
  • 车辆load-handling device与port高度/方向/载荷能力是否兼容；
  • port、车辆或固定transfer unit是否被占用或发生故障；
  • pick动作、载荷传感和身份/状态确认是否成功。
研究表达方法：先写“物理或信息条件为什么没有满足”，再写“可能由哪个控制系统负责”。不要在架构未知时用PLC、MES或WMS代替因果解释。

VDA 5050不是调度方案

它主要提供它明确没有提供
fleet control与不同厂商移动机器人之间的统一order/state通信方式；车辆、动作、状态和错误等通用表达。最佳dispatching/routing算法；交通管理逻辑；安全要求；外围设备及MES/PLC/WMS接口；网络安全和项目责任分配。

因此不能说“VDA 5050帮助我们完成AGV调度”。更准确的是：它帮助车队控制系统把已经形成的订单传给车辆并接收状态，但如何产生任务、怎样选车和怎样优化仍由项目设计决定。

当前案例的Fact—Inference—Unknown示范

证据状态当前能够说什么
FACT一般AGV研究区分fleet sizing、dispatching、routing、traffic、parking和charging；VDA 5050定义fleet control—mobile robot接口和最低功能。Cell-finishing文献支持formation、aging和EoL等工艺功能。
INFERENCE如果这些cell-finishing节点之间由移动机器人运输tray，那么车辆数量和任务分配可能影响tray waiting，并进一步影响blocking/starvation；固定handover可能把区域运输与精密装卸分开。
UNKNOWN目标场景是否真的使用AGV或VDA 5050；谁创建请求；直接交接还是conveyor/lift/gantry；车辆数量与能力；layout、路线、优先级、充电、故障恢复及空盘逻辑。
复盘后的检查方法：先判断这是“规划几台车”“运行时派哪台车”“车辆怎么执行”还是“设备怎样交接”，再讨论具体系统名称。
